§1

What the PoC has to prove

That a consultant can hand the tool an approved FS and get back a Technical Design good enough to send to an ABAP developer without rewriting it — and that they stay in control of every sentence on the way there.

Three things follow from that, and they are the acceptance bar:

  • Quality per type beats breadth of types. One convincing Interface TD is worth five thin ones.
  • Nothing is invented. Enhancement names, field lengths and process steps either come from the sources or are recorded as open questions. A fabricated BAdI costs the ABAP team more than the tool saves.
  • The consultant's edits survive. Hand-written text is never silently overwritten by a regeneration.

Out of scope for the PoC: Solution Manager or Jira integration, approval workflow and e-signature, multi-user co-editing of one design, and any automatic write-back to SAP.

§3

The document model

A TD is a type-invariant spine plus a type extension pack. Roughly 70% of the document is the same whatever is being built, which is what makes adding a type affordable: one schema fragment and one template block, not a new product.

The spine — twelve sections

Sections are individually switchable per design, so a small enhancement is not forced to carry an empty integration chapter. The generator's own prompt file already marks several sections as skippable; this makes that a UI control rather than a prompt edit.

#SectionCarries
1Document ControlVersion, author, reviewers, related FS, transport, sign-off table
2Requirement UnderstandingThe requirement restated technically, traced to FS clauses
3Open QuestionsUnanswered clauses and source conflicts — never guesses
4Proposed SolutionStandard vs custom, alternatives considered, chosen approach and why
5Architecture OverviewSystems, components, and the diagram set for this type
6Object InventoryEvery Z-object with name, type, package and purpose
7Data DesignDDIC objects, CDS views, field-level detail, persistence and retention
8Processing LogicStep-by-step logic in functional language — no ABAP
9Integration DesignInbound and outbound interfaces, protocols, triggers, reconciliation
10Security & AuthorizationAuth objects, roles, sensitive data handling, logging hygiene
11Error HandlingException paths, Application Log, restart and reprocessing
12Testing & ValidationUnit and integration scenarios, negative paths, acceptance criteria

Type extension packs

TypePoCAdds to the spine
ReportBuiltSelection screen, ALV/output layout, sorting and subtotals, spool behaviour
InterfaceBuiltMessage structure, field mapping table, protocol and middleware, trigger and frequency, retry and reprocessing, idempotency, monitoring (AIF / SXMB_MONI)
EnhancementBuiltEnhancement point identification, impact on standard behaviour, upgrade and regression risk, fallback where no BAdI exists

Each type is one JSON schema in a registry, keyed by type ID, declaring its sections and per-field types (text, table with named columns, choice). The schema drives the prompt and the Word render, so the two cannot drift apart.

§4

Input model

Exactly one primary source, plus up to five supporting documents. Every document declares a role, and the role decides what it is allowed to do.

RoleCountContributesPrecedence
Primary — approved FS or BRDExactly 1The requirement of recordWins every conflict
Meeting notes / workshop minutes0–5Detail and clarificationAdds; cannot override primary
Mapping / sample data0–5Field-level tablesAuthoritative for field detail
Reference TD0–2Format and tone onlyNever contributes content
Screenshots / mock-ups0–5Layouts, selection screensAdds
Standards & naming conventions0–2Z-naming, package and transport rulesOverrides model defaults
The failure this design prevents

Someone uploads FS v1 and FS v2. The model merges them silently, and the TD contains a requirement that was removed in review. The output looks confident, nobody catches it, and the PoC is over. Hence: one primary, declared precedence, and conflicts surface as open questions rather than being resolved.

Evidence extraction (D10)

Each document is parsed once into a structured evidence pack — facts, tables and open items, each carrying a source reference — and the section prompts consume the pack, never the raw files. Without this, six documents multiplied by twelve sections exhausts the context window and makes the cost per design scale with document count.

The evidence pack is also what makes multi-source safe to trust: every generated statement can point at document, clause, which is what the review panel displays.

§5

Workflow and progress

Five stops, fixed for the life of a design. The rail is mounted once by the SPA shell, above the router, so changing step swaps only the panel beneath it.

StopThe consultant doesThe system does
1 · SourceUploads the primary FS and any supporting documents, assigning a role to eachParses each document and builds the evidence pack; reports what it found and what it could not
2 · ScopeConfirms the requirement understanding, TD type, system context, section list, diagram set; answers open clausesSuggests type and context from the evidence; flags conflicts between sources
3 · GenerateWaits, or leaves — generation continues server-sideOne LLM call per section against the evidence pack, streaming per-section state
4 · ReviewReads, edits, revises and confirms each sectionRuns quality checks; regenerates single sections on request; tracks provenance
5 · DeliverDownloads the Word documentRenders confirmed JSON into the corporate template; stores the version on the session

Rules the rail obeys

  • The underline is weighted by sections confirmed — never elapsed time, never a creep to 90%.
  • It never runs backwards. Regenerating one section at stop 4 does not drop the rail to stop 3.
  • A completed stop is a link; consultants revisit scope constantly and must not restart to fix a package name.
  • State lives on the server session, so closing the tab and returning tomorrow restores the same stop, mid-review.
  • A stop can show needs attention (unanswered questions) or failed (generation error, retry from here) without losing its place.
§6

Generation and guardrails

One LLM call per section. Each call receives the section's schema, the evidence pack, the confirmed scope, and the sections already confirmed — and must return strict JSON matching the schema. A malformed response gets exactly one repair retry before the section is marked failed and offered for manual retry.

Guardrails, enforced in the prompt and surfaced in the UI

  • No invented SAP object names. BAdIs, exits, BAPIs and enhancement spots are named only when they can be grounded; otherwise the text says which enhancement area to investigate and assigns validation to the ABAP team. Anything unverified is flagged in review.
  • No ABAP. This is a design, not an implementation — no class names, method signatures or code blocks.
  • No silent gap-filling. An unanswered clause becomes an open question in section 3 and travels into the delivered document.
  • Naming conventions are honoured where a standards document was supplied, and flagged as assumed where it was not.
  • Reference TDs are style-only. Content bleed from another client's design is both a quality failure and a confidentiality one.
Quality checks shown in review

The checks panel is what makes the guardrails visible rather than merely instructed: unverified enhancement names, field definitions that contradict the FS, sections with no negative-path test case, and mandatory schema fields left thin. Each finding offers a targeted fix rather than a whole-section regeneration.

§7

Diagrams

Diagrams are generated as Mermaid source, rendered to SVG in the browser, approved or edited by the consultant, then converted to PNG and embedded by the docxtemplater image module. This is the only place in the product where an image is generated, and it is generated from structured text — never drawn by an image model.

TypeFunctional / process flowTechnical architectureAlso
ReportMandatory—Data-source diagram when several CDS views or tables join
InterfaceOptionalMandatorySequence diagram mandatory — lifelines, numbered messages, ack and error branch
EnhancementMandatory—Must show where in the standard process the enhancement fires
FormMandatory—Trigger → output determination → form → channel
FioriMandatory (screen flow)MandatoryApp → OData → CDS → backend, plus Launchpad and gateway

Two implementation details worth budgeting for: render SVG to PNG at 2–3× scale or the diagram is visibly soft in Word, and give the image module explicit dimensions or the picture floats unpredictably in the page flow.

§8

Review and edit

Both editing modes exist (D7). The design work is entirely in how they coexist, because regeneration destroys manual edits and must never do so silently.

Collision rule

Once a section carries manual edits, Regenerate asks which is meant:

  • Revise including my edits — the edited text is sent as the base. Default.
  • Regenerate from scratch — edits are discarded, and the dialog says so plainly.

Further rules

  • Section-level only. Whole-document regeneration after eight confirmed sections is catastrophic and does not exist in the UI.
  • Provenance per section — AI drafted / AI revised / human edited. Reviewers need to know what a person vouched for, and the share of hand-edited sections is the single best measure of how good generation actually is.
  • The last few versions of each section are kept on the session, so Revise is reversible. It is JSON; it is cheap; reversibility is what makes people willing to press the button.
  • Editing is not confirming. They are separate acts — confirmation is what drives the rail.
  • No free rich-text editor. Anything the Word template cannot represent disappears silently at render. Use a per-field-type editor: textarea for text fields, editable grid for table fields.
§9

Delivery and the template contract

The renderer fills a corporate Word template with confirmed JSON and returns base64, exactly as the FS agent's render_docx node already does. Until the official template arrives (O1), development runs against a placeholder contract so that swapping in the real one is a file swap and a tag mapping — not a redesign.

Tag contract

{doc_title}  {doc_version}  {author}  {transport}   // scalars
{#object_inventory}{object}{type}{purpose}{/object_inventory}   // table loop
{#open_questions}{question}{raised_by}{/open_questions}
{%architecture_diagram}                              // image tag
{#sections}{heading}{body}{/sections}                // optional sections
Word breaks docxtemplater tags silently

A placeholder typed in Word can be split across XML runs by autocorrect, spellcheck or a mid-word formatting change. The tag then renders as nothing, with no error. Any supplied template needs a tag-normalisation pass, and that pass has to be repeated whenever someone edits the template in Word. Budget for it as recurring work, not a one-off.

What is needed to close O1: the .docx or .dotx itself; which sections delivery governance treats as mandatory; and the header, footer, version-table and document-control conventions. Absent all three, a defensible default is authored from the structure already in the generator's prompt file.

§10

Architecture

A React SPA served by the axet-spa-app node, talking to http-in / http-response endpoints on the same aXet.flows instance. The SPA reads window.AXET_CONFIG.flowsBaseUrl for the API base and sends withCredentials: true so the Okta session cookie reaches the backend.

Endpoints

POST   /td/session                          create, returns sessionId
POST   /td/session/:id/documents            upload + role
DELETE /td/session/:id/documents/:docId
POST   /td/session/:id/extract              build evidence pack
POST   /td/session/:id/scope                type, context, sections, answers
POST   /td/session/:id/generate             returns immediately
GET    /td/session/:id                      full state — the poll target
PUT    /td/session/:id/section/:key         manual edit
POST   /td/session/:id/section/:key/revise  AI revision + instruction
POST   /td/session/:id/section/:key/confirm
POST   /td/session/:id/render               docx, base64
GET    /td/designs                          dashboard list

Node mapping

  • deptapps-app-auth-okta — authentication, roles from the users collection
  • axet-spa-app — serves the built SPA, injects AXET_CONFIG
  • function — session controller, evidence extraction, prompt building, response parsing, render
  • enabler-llm — one node, called per section
  • nosql-persist / nosql-find-one / nosql-query / nosql-remove — session and design store

Session document

{
  sessionId, owner, createdAt, updatedAt, status,
  documents: [{ docId, name, role, pages, parsedAt }],
  evidence:  { facts[], tables[], openItems[], conflicts[] },
  scope:     { tdType, release, module, package, transport,
               sections[], diagrams[], answers{} },
  sections:  { <key>: { status, provenance, content,
                        history[], checks[], sources[] } },
  render:    { fileName, base64, version, renderedAt }
}
Open: synchronous or polled generation (O2)

Per-section generation assumes 10–20 seconds a call. If http-in enforces a hard request timeout in this deployment, generation must be fire-and-poll: /generate returns immediately and the SPA polls GET /td/session/:id. The UI is drawn for that already; only the endpoint contract changes. This needs confirming against the actual runtime before §10 is built.

§11

Limits and non-functionals

  • Documents — 1 primary + 5 supporting, 20 MB each, .docx and .pdf.
  • Authentication — Okta via the existing config; roles from the users collection, not Okta groups.
  • Persistence — every design is a session document; work survives reload, tab close and container restart.
  • Confidentiality — client FS content stays inside the tenant. This is the reason PDF conversion via an external API is refused in D4.
  • Accessibility — keyboard reachable throughout, visible focus, the rail exposed as an ordered list with current-step state, and no meaning carried by colour alone (the check pills pair colour with a label).
  • Auditability — provenance per section plus render versions give a defensible trail of what the AI wrote and what a person changed.
